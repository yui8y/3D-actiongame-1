# ゲームタイトル(仮):未定(作業名:Dash Collector)

> 就職活動用ポートフォリオ(ゲームエンジニア志望)/ 1人制作・約3週間 / Unity + C#
> 「未定」と書いた項目は、制作を進めながら決定する。

## 1. コンセプト

ウサギがカフェの中を駆け回り、巡回する敵を避けながら、制限時間内にコーヒーを全部回収する3Dアクション。
「ダッシュをいつ使うか」の判断が面白さの中心。

## 2. ターゲットとプレイ時間

- **ターゲット**:ゲームに慣れていない人でも遊べる操作量
- **1プレイ**:未定(制限時間はScriptableObjectで調整するため、テストプレイで決める)
- **目標**:1回のプレイが数分以内に終わり、すぐリトライできること

## 3. ゲームの流れ(タイトル → プレイ → リザルト)

| シーン | 内容 |
|---|---|
| **Title** | タイトル表示、スタート、操作説明(1枚)、終了 |
| **Game** | 飲み終わったコーヒーを集めて換金する。ポーズ可能 |
| **Result** | クリア/ゲームオーバー表示、リトライ、タイトルへ戻る |

```
Title → Game → Result → (Retry → Game / Title)
```

## 4. 操作方法(キーボード/パッド)

| 操作 | キーボード | ゲームパッド |
|---|---|---|
| 移動 | WASD | 未定(スティック想定) |
| ダッシュ | スペース | 未定 |
| ポーズ | Esc | 未定 |
| メニュー決定・選択 | Enter | 未定 |

-入力は両デバイスを**同じ操作の設定(Action Map)**にまとめ、どちらでも遊べるようにする。
- 対応パッドの種類(Xbox系/PS系など)は未定。

> **Action Map**:「ダッシュ=Shiftキー または パッドのボタン」のように、操作と入力機器の対応を一か所で管理する仕組み(Input System の機能)。

## 5. ゲームルール(勝利条件・敗北条件・スコア)

- **勝利条件**:制限時間内にステージ上のコーヒーをすべて回収する
- **敗北条件**:①時間切れ ②敵に接触(接触時の扱い:即ゲームオーバー / ダメージ制は**未定**)
- **ダッシュ**:一瞬速く動ける、回避行動。使用後にクールダウン(再使用までの待ち時間)がある
- **スコア**:MVPでは回収数と残り時間を表示するのみ。ランク(S/A/B)は「あれば良い」
- **数値**(制限時間、コーヒーの数、敵速度、クールダウン):制限時間は1〜2分(仮)。他は未定。ScriptableObjectで調整する

## 6. 実装機能一覧

### MVP(必須)
- プレイヤー:移動、ダッシュ(クールダウン付き)
- コーヒー(1種類)の回収。配置は固定(ランダム化は「あれば良い」)
- 敵1種類:ウェイポイント巡回(決めた地点を順に歩く)のみ
- 状態管理:Playing / Paused / Clear / GameOver State パターンで設計する
- シーン遷移:Title → Game → Result(リトライ、タイトルへ戻る)
- キーボード+ゲームパッド対応(ポーズ、メニュー操作を含む)
- UI:HUD(残り時間・回収数)、タイトル、ポーズ、リザルト
- サウンド:BGM 1曲、SE数個(回収・ダッシュ・被弾・クリア・ゲームオーバー)
- ScriptableObjectによるパラメータ調整
- ビルド、README、プレイ動画

### あれば良い(MVP安定後、上から順に検討)
1. リザルトに回収数・残り時間・簡易ランク
2. 回収時の簡易エフェクト
3. ダッシュ中の無敵判定
4. 難易度切り替え(ScriptableObjectの差し替え)
5. ベストタイム保存(PlayerPrefs)
6. 敵の2種類目(速度違い程度)
7. コーヒー配置のランダム化(候補地点から選ぶ)

### やらない
- 複数ステージ、ストーリー、チュートリアル画面
- NavMeshによる追跡AI
- 自作モデル・自作アニメーション
- セーブ/ロード、音量調整以外の設定画面、ローカライズ
- コーヒーの種類違い、パワーアップ、ランキング、実績、オンライン要素
- カメラの高度な演出

> **ウェイポイント巡回**:あらかじめ置いた目印の地点を、順番に歩き続ける単純なAI。
> **PlayerPrefs**:Unityに用意されている、小さなデータを手軽に保存する仕組み。

## 7. 技術的な方針

### シーン構成
- `Title` / `Game` / `Result` の3シーン。シーン間のデータ(クリア結果など)の受け渡し方法は未定。

### 状態管理の方針
- ゲーム全体の状態を **Playing / Paused / Clear / GameOver** の4つで管理し、状態ごとに「許可する処理」を分ける。
- 状態の変更窓口を1か所にまとめる(詳細設計は第1週に決定)。
- ポーズ方法(`Time.timeScale` の利用有無)は未定。
- リトライ時に前回の状態が残らないよう、初期化を設計に含める。

### ScriptableObjectで調整するパラメータ
| 対象 | パラメータ(案) |
|---|---|
| プレイヤー | 移動速度、ダッシュ速度、ダッシュ時間、クールダウン |
| 敵 | 巡回速度、待機時間 |
| ステージ | 制限時間、必要コーヒー数 |

> **ScriptableObject**:数値などの設定データを、シーンとは別のファイル(アセット)として保存できるUnityの仕組み。コードを書き換えずに調整できる。

### 使用するUnityパッケージ
- Input System(予定)
- 他のパッケージ:未定

### 環境
- Unityバージョン:**未定**
- レンダリングパイプライン(Built-in / URP):**未定**(アセット選定の前に決める)
- 移動方式(CharacterController / Rigidbody):未定
- カメラ:固定の俯瞰を想定(未確定)
- 対象プラットフォーム:Windowsビルドを想定

> **レンダリングパイプライン**:画面の描画方式。アセットが対応している方式と合わないと、見た目が崩れる(ピンク色になる等)ことがある。

## 9. 開発スケジュール(週単位・案)

| 週 | 内容 |
|---|---|
| **第1週** | 仮の形(キューブとカプセル)でMVPの骨格を作る:移動・ダッシュ・回収・敵・状態管理・シーン遷移。**一度ビルドして動作確認**。アセットを決定。友人1人に遊んでもらう。 | 
| **第2週** | アセット差し替え、UI、サウンド、ScriptableObject整理、バランス調整 |
| **第3週** | バグ修正、他の人によるテストプレイ、「あれば良い」から1〜2個、README・設計資料・プレイ動画。**後半は新機能禁止** |

- 設計の記録(状態遷移図、クラス構成など)は、最終週にまとめず毎週少しずつ残す。

## 10. 想定リスクと対策

| リスク | 対策 |
|---|---|
| アセット探しと統合に時間がかかる | 第1週末で期限を切る。決まらなければ妥協する |
| 「あれば良い」に手を出して時間が溶ける | MVP完成後にのみ着手。第3週後半は新機能禁止 |
| ダッシュの判定バグ(壁抜け、敵との接触) | 無敵判定は後回し。移動方式を最初に1つに決める |
| パッドでメニューを操作できない | UI作成時から、最初に選択されるボタンの指定を含めて作る |
| ポーズ・リトライ後に状態が残るバグ | 第1週に状態管理を固めてから他機能を載せる |
| エディタでは動くがビルドで動かない | 第1週からビルドして確認する |
| ライセンス問題 | 使用アセットごとに条件を記録する |
| 面白さが足りない | 仮の形の段階でプレイし、面白さを先に確認する |
